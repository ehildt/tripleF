# Contributing to tripleF (3F)

Thanks for your interest in contributing! tripleF is a source-available agentic AI workbench, and we welcome bug reports, feature ideas, and proposed contributions.

Please read this guide before opening an issue or pull request. By participating, you agree to abide by our [Code of Conduct](CODE_OF_CONDUCT.md).

## Licensing and permission

tripleF's first-party code is licensed under the [PolyForm Strict License 1.0.0](LICENSE). The public license permits noncommercial use, but it does not permit modification or redistribution.

Open an issue and obtain permission before creating a patch or pull request. Code contributions require a separate written contributor agreement granting the copyright holder the rights needed to distribute and commercially license the contribution. Do not submit code until that agreement is in place.

## Getting started

- **Read the docs first.** The [technical wiki](.wiki/index.md) explains the architecture, the harness, the REST API, BullMQ, Socket.IO, and the dashboard. The [Introduction](.wiki/0-introduction.md) is a good place to start.
- **Set up the stack.** Follow the [Quick Start](.wiki/0.1-quick-start.md) to get a local environment running.
- **Find something to work on.** Check the [issues](https://github.com/ehildt/tripleF/issues) for open work, or open a new one to discuss your idea.

## Opening an issue

- **Search first** to avoid duplicates.
- Use the appropriate [issue template](.github/ISSUE_TEMPLATE/) (bug report or feature request) and fill it out completely.
- For bugs, include steps to reproduce, expected vs. actual behavior, and your environment (OS, Node/pnpm versions, Ollama setup).

## Making changes

1. **Discuss and obtain permission before you build.** Open an issue first to discuss what you would like to change or add. Do not modify the code until the proposal has been approved and the required contributor agreement is in place.
2. **Branch from `main`** and keep changes focused on a single concern.
3. **Follow the conventions** in the relevant skill docs:
   - Vue 3 / frontend: `dashboard/` — see the Vue conventions.
   - NestJS / server: `server/` — see the NestJS conventions.
   - Styling: design tokens and scoped CSS.
4. **Add or update tests.** We use Vitest in both workspaces. New behavior should be covered.
5. **Keep quality gates green.** Pull requests must pass CI before they can be merged. Locally, run the lint, type-check, and test scripts in the affected workspace.

## Commit & versioning

- This project follows [Semantic Versioning](https://semver.org/).
- We use [Changesets](https://github.com/changesets/changesets) to manage releases. Add a changeset for user-facing changes (see `.changeset/`).
- Write clear, conventional commit messages.

## Pull requests

- Use the [pull request template](.github/PULL_REQUEST_TEMPLATE.md).
- Reference the issue your PR addresses.
- Keep the diff as small as possible and rebase onto the latest `main`.
- CI must pass; a maintainer will review and may request changes.
