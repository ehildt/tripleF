# 1.6. Memory Cognition — JSON Schema Reference

Field-by-field reference for the **memory cognition** JSON — the AI's structured
understanding of the user. It reflects the schema **as it exists today**; no
fields beyond what the code currently holds.

Source of truth (read these before editing):

- `apps/memory/src/modules/qdrant/models/memory-cognition.model.ts` — Zod schemas + merge logic
- `apps/memory/src/modules/qdrant/constants/memory-profile-prompt.constant.ts` — the LLM prompt that emits the JSON
- `apps/memory/src/modules/qdrant/services/memory-cognition.service.ts` — insight/episode upserts
- `apps/memory/src/modules/persistence/services/memory-cognition-profile.repository.ts` — Postgres storage
- `apps/memory/src/modules/qdrant/services/memory-overrides.service.ts` — system variables
- `apps/memory/src/modules/qdrant/dtos/memory-cognition-snapshot.dto.ts` — dashboard read shape
- `apps/memory/prisma/schema.prisma` — `MemoryCognitionProfile` model

## 1. What "memory cognition" is

The memory app keeps the AI's understanding of the user in **three artifacts**,
all derived (never the fact store):

| Artifact | Storage | Role |
| --- | --- | --- |
| **Profile document** | Postgres (`memory_cognition_profile.profile`, one row per space) | The **routing map**: stable identity + durable traits as short topic strings. Always-on respond context. |
| **Insights** | Qdrant (points tagged `cognition` + `insight`) | The **depth** behind those topics: specific models, past statements, working nuances. Probed by embedding at respond time. |
| **Episodes** | Qdrant (points tagged `cognition` + `episode`) | **Short-term conversation memory**: one sentence per turn on what happened. Recalled by a recency-blended probe. |

The profile is a single living JSON document grown by **patches** (the
`memoryProfile` queue job emits a delta, never the whole document). Insights and
episodes are separate records that point back into the profile via a `path`
payload (insights) or stand alone as turn arcs (episodes).

---

## 2. Profile document schema

The profile document is the JSON stored in the `profile` column. **Every field
is nullish (optional)** — a field the model does not know is an *omission*, and
a field set to `null` is an explicit *delete*.

```jsonc
{
  "name": "Sam",                    // string | null — user's name or preferred handle
  "language": "en",                 // string | null — BCP-47-ish ("en", "de")
  "timezone": "Europe/Berlin",      // string | null — IANA name or city
  "expertise": ["TypeScript", "NestJS"], // string[] | null — skills and domains
  "goals": ["ship the dashboard"],  // string[] | null — active goals/aspirations
  "communication": {                // object | null — how the user wants to be answered
    "style": "concise",             //   string | null
    "detailLevel": "high",          //   string | null
    "formality": "casual"           //   string | null
  },
  "preferences": {                  // Record<string, string> | null — free-form key-value
    "editor": "vim"                 //   tooling / environment / format preferences
  },
  "likes": ["cars"],                // string[] | null
  "dislikes": ["cilantro"],         // string[] | null
  "interests": ["anime"],           // string[] | null — topics the user keeps returning to
  "persona": {                      // object | null — the AI's own identity, shaped by the user
    "name": "Sam",                  //   string | null — the name the user gave the AI
    "role": "coding assistant",     //   string | null — the role the user assigned
    "personality": "patient",       //   string | null — short character description
    "greeting": "Hey, I'm Sam",     //   string | null — how the AI introduces itself
    "voice": {                      //   object | null — how the AI should speak
      "tone": "friendly",           //     string | null
      "formality": "casual"         //     string | null
    }
  },
  "corrections": {                  // Record<string, string> | null — learned behavioral rules
    "lint-before-commit": "always run lint before committing"  // slug → imperative directive
  }
}
```

### Field table

| Field | Type | Nullish | Notes |
| --- | --- | --- | --- |
| `name` | `string` | yes | User's name or preferred handle, when known. |
| `language` | `string` | yes | Primary conversation language (BCP-47-ish). |
| `timezone` | `string` | yes | Coarse location the user works from (IANA name or city). |
| `expertise` | `string[]` | yes | Demonstrated skills and domains. |
| `goals` | `string[]` | yes | Active goals and aspirations — the most durable cognition. |
| `communication` | `object` | yes | How the user wants to be answered. |
| `communication.style` | `string` | yes | |
| `communication.detailLevel` | `string` | yes | |
| `communication.formality` | `string` | yes | |
| `preferences` | `Record<string, string>` | yes | Tooling / environment / format preferences (free-form). |
| `likes` | `string[]` | yes | |
| `dislikes` | `string[]` | yes | |
| `interests` | `string[]` | yes | Topics the user keeps returning to. |
| `persona` | `object` | yes | The AI's own identity as the user has shaped it. |
| `persona.name` | `string` | yes | The name the user gave the AI. |
| `persona.role` | `string` | yes | The role the user assigned the AI (e.g. "coding assistant"). |
| `persona.personality` | `string` | yes | Short character description the user gave the AI. |
| `persona.greeting` | `string` | yes | How the AI introduces itself, when the user set one. |
| `persona.voice` | `object` | yes | How the AI should speak. |
| `persona.voice.tone` | `string` | yes | |
| `persona.voice.formality` | `string` | yes | |
| `corrections` | `Record<string, string>` | yes | Learned corrections — behavioral rules the user taught the AI. Key = short slug, value = imperative directive. |

### Normalization rules

Before store, `normalizeCognitionProfile` strips residual noise:

- `null` / `undefined` fields → dropped
- empty strings → dropped
- empty arrays → dropped
- empty objects → dropped
- string values are trimmed

Cleaning recurses into nested objects, so sub-documents (`communication`,
`preferences`, `persona.voice`) are cleaned at every depth.

An all-empty verdict yields `undefined` (a no-change answer).

## 3. Insights schema

One derived insight the profile job may emit. Stored as a Qdrant point (not
inside the profile document).

```jsonc
{
  "text": "The user prefers the 911 over the Cayman.", // string — required, one self-contained sentence
  "path": "likes.cars"                                  // string — optional, "field.keyword"
}
```

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `text` | `string` | yes | One self-contained sentence, third person, leads with the topic. Capped at `INSIGHT_TEXT_LIMIT` (500 chars). |
| `path` | `string` | no | Dot-joined `field.keyword` (e.g. `likes.cars`) routing the insight back to the profile facet it deepens. Normalized to lowercase, dash-joined segments (`likes.software engineering` → `likes.software-engineering`). Malformed paths are dropped (text still stores). |

Insight Qdrant point payload (as returned by the dashboard via `MemoryItemDto`):

| Field | Notes |
| --- | --- |
| `id` | Deterministic UUID seeded on `{space}\|cognition\|insight\|{text}` — repeats overwrite silently. |
| `text` | The insight sentence. |
| `role` | `"assistant"` (cognition is the AI's own understanding). |
| `tags` | `["cognition", "insight"]`. |
| `path` | The normalized `field.keyword` routing key (optional). |
| `memoryCognition` | The cognition space key. |
| `sessionId` / `conversationId` / `requestId` | Provenance of the turn that produced it. |

## 4. Episode schema (short-term conversation memory)

One episode the profile job may emit — a single sentence recording what the
turn was about (the interaction arc: asked / did / decided / left open). Stored
as a Qdrant point, one per turn.

```jsonc
{
  "episode": "Helped the user debug the memory app's probe." // string — optional, one sentence, past tense
}
```

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `episode` | `string` | no | One sentence on what the turn was about. Capped at `EPISODE_TEXT_LIMIT` (500 chars). Omitted (or null) for trivial turns. |

Episode Qdrant point payload:

| Field | Notes |
| --- | --- |
| `id` | Deterministic UUID seeded on `{space}\|cognition\|episode\|{requestId}` — a retried job overwrites in place rather than duplicating. |
| `text` | The episode sentence. |
| `role` | `"assistant"`. |
| `tags` | `["cognition", "episode"]`. |
| `memoryCognition` | The cognition space key. |
| `sessionId` / `conversationId` / `requestId` | Provenance of the turn. |
| `created_at` | Stamped at upsert — powers the recency-blended probe. |

### Recency-blended probe

At respond time the episode probe ranks candidates by a recency-blended score
rather than raw cosine similarity:

```
final = $score + weight · exp_decay(created_at, target=now, scale, midpoint)
```

- `weight` — how much recency may break topical ties (`episodeRecencyWeight`).
- `scale` — decay horizon in seconds; an episode `scale` old loses half its recency bonus (`episodeRecencyScaleSeconds`).
- `midpoint` — decay curve midpoint (`episodeRecencyMidpoint`).
- `episodeProbeLimit` — max episode records injected into the respond context per turn.

All four are system variables (see §9).

## 5. Response wrapper (the LLM verdict)

The `memoryProfile` job must answer with exactly one JSON object, validated by
`memoryProfileResponseSchema`:

```jsonc
{
  "profile": { /* profile document patch — see §2 */ }, // object | null
  "insights": [ /* see §3 */ ],                         // array, max 8
  "episode": "…"                                        // string | null — see §4
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `profile` | profile document \| `null` | A **patch**, never the whole document. `null` = nothing durable learned (existing document stays). |
| `insights` | `Array<{ text, path? } \| string>` | New derived depth only. Max 8 per turn (`INSIGHTS_MAX_PER_TURN`). Bare strings are coerced to `{ text }`. |
| `episode` | `string` \| `null` | One sentence on what the turn was about; omitted/null for trivial turns. |

| `insights` | `MemoryItemDto[]` | The derived insight records. |

## 8. Merge semantics (patch rules)

The model emits deltas; `mergeCognitionProfiles` resolves them over the stored
document:

- **Omitted field** → kept as stored.
- **`null` field** → removed (the patch's deletion list).
- **Any other value** → replaces the stored value.
  - Nested `communication` / `preferences` / `persona` (and `persona.voice`) / `corrections` are **deep-merged** — emit only the sub-fields/keys you are changing; a `null` correction key removes that correction.
  - Arrays (`expertise`, `goals`, `likes`, `dislikes`, `interests`) are **replaced wholesale** — the patch must re-emit the complete array when it touches one.
- A patch that produces no effective change skips the write.
- `isAllFieldsNullWipe` guards against an accidental "forget everything" patch (all-null over every stored field) — the stored document is kept and the event logged.

## 9. System variables (memory-overrides)

Global settings layered over env defaults, persisted in the shared
`provider_overrides` row `memory`, restored on boot, and editable via
`PUT /memory-overrides` (see **1.1**).

| Variable | Env baseline | Default | Clamp | Purpose |
| --- | --- | --- | --- | --- |
| `cognitionLimit` | `MEMORY_COGNITION_LIMIT` | 5000 | 500–32000 | Profile document character cap (serialized JSON size). |
| `episodeRecencyWeight` | `MEMORY_EPISODE_RECENCY_WEIGHT` | 0.3 | 0–1 | How much recency may break topical ties in the episode probe. |
| `episodeRecencyScaleSeconds` | `MEMORY_EPISODE_RECENCY_SCALE_SECONDS` | 604800 (1 week) | 60–31536000 | Decay horizon — an episode this old loses half its recency bonus. |
| `episodeRecencyMidpoint` | `MEMORY_EPISODE_RECENCY_MIDPOINT` | 0.5 | 0.01–0.99 | Decay curve midpoint. |
| `episodeProbeLimit` | `MEMORY_EPISODE_PROBE_LIMIT` | 3 | 1–10 | Max episode records injected into the respond context per turn. |

## 10. AI-side fields: `persona` and `corrections`

The profile document holds **both** sides of the relationship:

- The **user-side** fields (§2, everything except `persona` and `corrections`) — who the user is.
- The **`persona`** field — who the **AI** is, as the user has shaped it: the
  name the user gave the AI, the role they assigned, a short character
  description, a greeting, and a voice (tone/formality).
- The **`corrections`** field — behavioral rules the user taught the AI after
  it got something wrong: a `Record<string, string>` keyed by a short slug,
  where the value is the imperative directive ("always …" / "never …"),
  optionally with a brief why.

Both are **model-derived** (the `memoryProfile` job extracts them from the
conversation — e.g. "I'll call you Sam" → `persona.name: "Sam"`; "don't use
mocks" → `corrections["no-mock-db"]`), live in the **same** profile document,
and are **deep-merged** like the other nested objects. They are *not* probe
triggers: `flattenProfilePaths` (server side) ignores them, since the AI's
identity and learned rules are always-on context, not user topics to recall.
