# 1.7. The Memory App

The **memory app** (`apps/memory`) is 3F's second NestJS + Fastify process: the long-term memory service. It owns everything Qdrant — the semantic memory store, the AI cognition spaces, the constellation link graph, and the knowledge encyclopedia — plus the BullMQ **`vectorize` worker** that runs the background LLM jobs (fact extraction, cognition profiles, maintenance sweeps) off the request path.

- **Entry:** `apps/memory/src/main.ts` → `apps/memory/src/main.module.ts`
- **Dev port:** `3400` · **API base:** `/api/v1` · **Docs:** `/api-docs`
- **Queue:** consumes `VECTORIZE_QUEUE` (KeyDB); the server produces it — see **1.3**
- **Stores:** Qdrant (vectors) + the shared PostgreSQL tables it owns rows in (`MemoryCognitionProfile`, ledgers, link-graph tables, its share of `DeadLetterJob` and the `memory` provider-overrides row)

## Why a separate process?

Because memory work is LLM-heavy and latency-insensitive. Embedding turns, rewriting the cognition profile, and adjudicating consolidations are exactly the work you do **not** want in the process that answers users. The split also isolates failure: a memory outage must never break a chat turn — every server-side call into memory degrades to "no memory this turn", and the background jobs retry on the queue.

## Topology

```
SERVER (harness)                                  MEMORY APP
───────────────                                   ──────────
interpret probe ── HTTP /qdrant/search/text ─────▶ QdrantController → Qdrant
sanitize context ─ HTTP /qdrant/memory/cognition ▶ cognition snapshot
execute sources ── HTTP /encyclopedia/select ────▶ EncyclopediaSelectService
remember tools ─── HTTP /qdrant/text … ──────────▶ sync store (embed + upsert)
memoryWrite ──┐
memoryProfile ┤
vectorize ────┴── enqueue VECTORIZE_QUEUE ───────▶ VectorizeProcessor
                                                       │ 10 job kinds (below)
                                                       ▼
                                              Qdrant · Postgres · Ollama
dashboard ── /memory-api proxy ──(dev Vite / prod nginx)──▶ all of it
```

The dashboard talks to the memory app **directly** (never through the server): dev via the Vite `/memory-api` proxy, prod via nginx — see **2-dashboard** and **1.1**. Internally the server reaches the same REST surface through the `memory-client` module (`MEMORY_URL`, default dev `http://memory:3400`).

## The vectorize worker — one queue, ten job kinds

`processors/vectorize.processor.ts` consumes `VECTORIZE_QUEUE` and dispatches by job name (`KNOWN_JOB_NAMES` — unknown names are never consumed, so a shared queue stays safe):

| Job                       | Handler                                 | What it does                                                                                                                                                                                                                                                                                                |
| ------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vectorize`               | step engine (`extract → embed → store`) | Per turn-side fact extraction: probes the partition first (`ALREADY STORED` block), extracts only genuinely new/refined facts, embeds, stores into `memory_partition` + writes the insert-ledger row. Text caps from `MEMORY_VECTORIZE_TEXT_*`.                                                                |
| `memory-write`            | `memory-write-job`                      | Classifier-gated: re-asks the model with the turn's gathered results and routes durable items via the remember decisions (prior-memory aware; `probedMemory` treated as already known).                                                                                                                        |
| `memory-profile`          | `memory-profile-job`                    | Runs after **every** answered turn: one dedicated call that patches the cognition profile document (merge semantics — see **1.6** §8), upserts insight records, and may emit one episode. Payload caps from `MEMORY_PROFILE_PAYLOAD_*`.                                                                          |
| `memory-consolidate`      | `memory-consolidate-job`                | Dedupe/merge sweep over the pending insert ledger with LLM verdicts `keep`/`redundant`/`merge` (never geometric). Auto-triggered per partition when pending ≥ `MEMORY_CONSOLIDATE_THRESHOLD` (50).                                                                                                              |
| `memory-relink`           | `memory-relink-job`                     | Collapses category variants and writes `topical` edges (plus neighbor links) into the link graph.                                                                                                                                                                                                              |
| `memory-reflect`          | `memory-reflect`                        | The friction screen: unreflected points vs near-neighbors, LLM friction verdicts (`contradiction`/`superseded`/`outdated`/`disagreement`) → `memory_friction` rows (`open`), losers marked superseded, never deleted. Caps: `MEMORY_REFLECT_BATCH_LIMIT`, `MEMORY_REFLECT_MAX_CANDIDATES`.                              |
| `memory-conviction`       | `memory-conviction`                     | Conviction synthesis over curated facts: `conviction` records into the **cognition** lane, `bridge` records into the **partition** lane with `evidence` citation edges. The model cites evidence by ordinal — provenance is deterministic. Caps: `MEMORY_CONVICTION_BATCH_LIMIT`, `MEMORY_CONVICTION_MAX_PER_CLUSTER`. |
| `memory-cluster`          | `memory-cluster-job`                    | Clusters the scope's link graph (semantic + topical + evidence edges), LLM-summarizes each changed cluster (`title` + `summary`) into `memory_cluster`; membership fingerprint is the drift signal. Min size `MEMORY_CLUSTER_MIN_MEMBERS`.                                                                     |
| `encyclopedia-consolidate` | `encyclopedia-sweep`                  | Deterministic supersede sweep: heals orphaned old-hash chunks left by a crashed re-index. No model, no adjudication (dedupe happens at retrieval). Ledger-driven; auto-triggered at `ENCYCLOPEDIA_CONSOLIDATE_THRESHOLD` (200) pending documents.                                                            |
| `encyclopedia-classify`   | `encyclopedia-classify`                 | One LLM call per stored document: labels it with the source-agnostic category + topic tiers, fanned out to every chunk via `setPayload`. Auto-triggered at `ENCYCLOPEDIA_CLASSIFY_THRESHOLD` (20).                                                                                                              |

Failures follow the BullMQ/DLQ philosophy everywhere: transient infra errors retry (embed timeouts become transient by design), deterministic failures (config errors, unparseable verdicts) are marked final instead of burning retries, and ledger rows are only marked swept/classified **after** the work landed — a crash mid-run always resumes from the oldest pending row.

## How a harness turn uses memory (the workflow)

1. **Intake / interpret** — when the classifier wants to clarify, the step probes the user's fact partition (`memory-partition-recall`-equivalent `searchByText`) and re-runs the classifier once with the provenance-labeled probe block injected; often the "ambiguity" resolves from memory.
2. **Execute** — the model may invoke the memory tools directly (scope-bound by `memoryPartition`/`memoryCognition`, threaded per request so a tool can never cross space boundaries); remember calls store synchronously via the memory client.
3. **Sanitize** — fetched/search sources are distilled through the encyclopedia (verbatim passages under a char budget — never summarized without provenance; `partitionScope` follows the session's memory partition) and indexed for later probes; when the select is unavailable the step falls back to full references. This is also where the AI's cognition is injected as always-on, marked-private system context when memory is enabled: the profile document always (it doubles as the routing map — profile values that token-match the prompt sharpen the insight query), plus the top insights, the recency-blended episode probe, and the conviction probe; with `graphRag` on the request, link-graph bridges join the context too.
4. **Respond** — the answer streams; then the post-response steps fire: `memoryWrite` (classifier-gated) and `memoryProfile` (every turn) enqueue their jobs, and `vectorize` enqueues both turn-sides for fact extraction.

Writes are therefore **never** on the request's critical path, and the whole subsystem is off when `MEMORY_ENABLED=false` — the harness behaves exactly like a stateless chat in that mode.

## The constellation (link graph / GraphRAG)

On top of the vector store, the memory app maintains a **link graph** per space — the "constellation" the dashboard renders as a force graph (see **2-dashboard**):

- **`memory_link`** edges — `semantic` (enforced kNN at store time, `MEMORY_LINK_NEIGHBORS` = 3 per dot, min score `MEMORY_LINK_SCORE_THRESHOLD` = 0.7), `topical` (suggested by the relink job, softer bar `MEMORY_LINK_TOPICAL_THRESHOLD` = 0.6, ignored by recall), `evidence` (conviction/bridge citations — exact, not similarity-derived).
- **`memory_friction`** rows — contradiction pairs from reflection, state-machined `open → resolved | dismissed`.
- **`memory_cluster`** rows — detected clusters with LLM titles/summaries.

Reads for the constellation honor `MEMORY_CONSTELLATION_NODE_LIMIT` (5000); link-graph reads are bounded by `MEMORY_LINK_READ_MAX`. Raising the score thresholds invalidates old edges semantics-wise — recompute them via `POST /qdrant/memory/links/recompute` (lazy backfill bounded by `MEMORY_LINK_BACKFILL_MAX_POINTS`). When the dashboard passes `graphRag=true` on `POST /harness`, the harness additionally probes this graph (bridges + cluster summaries) for the request's context.

## The encyclopedia

The encyclopedia (`ENCYCLOPEDIA_COLLECTION` = `memory-encyclopedia`, resolved per embedding model like the memory collection) is the **shared knowledge base**: fetched source documents are chunked (sentence-packed at `ENCYCLOPEDIA_CHUNK_CHARS` with one-sentence overlap), embedded, and stored with provenance (url/domain/content hash), then selected **verbatim** at retrieval:

- `POST /encyclopedia/select` — the read path used by the harness: Lane A selects from the request's current documents, Lane B probes previously persisted sources (global probe, `ENCYCLOPEDIA_PROBE_LIMIT` passages, neighbor-expanded by `ENCYCLOPEDIA_NEIGHBOR_EXPANSION`) — everything within `ENCYCLOPEDIA_BUDGET_CHARS`, cosine floor `ENCYCLOPEDIA_SCORE_THRESHOLD`. With `ENCYCLOPEDIA_PERSIST_ENABLED=false` selection is ephemeral (nothing stored).
- `POST /encyclopedia/index` — explicit indexing of a document (rejects oversize docs past `ENCYCLOPEDIA_MAX_DOCUMENT_CHARS`).
- Maintenance: consolidate (supersede sweep) → classify (category/topic) → reflect (friction screen) → cluster — same philosophy as the partition pipeline, driven by the `ENCYCLOPEDIA_*` thresholds and `_AUTO` flags.
- Read surfaces for the dashboard: `GET /encyclopedia` (chunks, filterable by `domain`/`partitionScope`), `/links`, `/frictions`, `/clusters`, plus `POST /encyclopedia/links/recompute`.

| `POST`   | `/qdrant/memory/cognition/insights` | Store one derived insight synchronously; `{accepted, id}` envelope                                          |

| `GET`    | `/qdrant/memory/frictions`        | Open/resolved friction pairs of a space                                                                       |

| Method | Path                            | Purpose                                                        |
| ------ | ------------------------------- | -------------------------------------------------------------- |
| `POST` | `/qdrant/memory/consolidate`    | Dedupe/merge sweep (optional `dryRun`, `limit`, all partitions by default) |
| `POST` | `/qdrant/memory/relink`         | Re-link a scope's graph (topical edges, category collapse)     |
| `POST` | `/qdrant/memory/reflect`        | Friction screen of a partition                                 |
| `POST` | `/qdrant/memory/conviction`     | Conviction synthesis (convictions + bridges)               |
| `POST` | `/qdrant/memory/cluster`        | Cluster detection + summaries                                  |
| `POST` | `/qdrant/memory/cognition/reflect` | Friction screen of a cognition space                        |

### System variables (`@Controller('memory-overrides')`)

| Method   | Path                | Purpose                                                                          |

| `GET`    | `/memory-overrides` | Effective values + env baselines + override flags + bounds (feeds SysCtl)         |

## Configuration

The memory app's env baseline lives in `apps/memory/.env` (boot-validated, restart-scoped): app server, Postgres, BullMQ (incl. `BULLMQ_VECTORIZE_CONCURRENCY`), Ollama, secrets, **Qdrant** (`QDRANT_URL`, `QDRANT_API_KEY`, `QDRANT_COLLECTION`, `QDRANT_EMBED_MODEL`, `QDRANT_VECTOR_SIZE`, `QDRANT_SCORE_THRESHOLD`, `QDRANT_EMBED_TIMEOUT_MS`, `MEMORY_ENABLED` and the `MEMORY_*` tuning), the **cognition**, **partition maintenance**, and **encyclopedia** pipelines. Everything tunable at runtime is layered through the memory-overrides system variables — see **1.6** §9 for the set and **1.8** for the layering rules.
